# M460 能力整合开发计划

更新时间：2026-06-09

## 1. 整合定位

本计划聚焦把 `M460_Series_BSP_CMSIS_V3.00.002` 中已经承担的采集、控制、告警、计算和 Modbus 能力迁入 `energy`。迁入方式不是恢复 `energy -> M460 -> 600 模块` 的 980 中间链路，而是把 M460 的能力拆成 `energy` 内部服务：

1. 下行采集继续以 600 节采集模块端 `01/81` 为主协议。
2. 600 显式控制命令统一由内部控制服务构造，再进入采集通道命令队列。
3. 标准实时表和当前态表成为页面、告警、JSON/TCP、Modbus 的共同数据源。
4. SOC/SOH、容量、告警过滤等长周期逻辑进入轮询外后处理，不写入采集线程。
5. 980 PC/网络端协议只作为旧语义和字段参考，不恢复为运行链路。

## 2. M460 能力分层

| 能力层 | M460 参考 | energy 落点 | 优先级 |
|---|---|---|---|
| 6 路下行采集 | `rs485.c`、`protocol_package.c` | `BatteryCollectorService`、`BatteryModuleRealtimeConsumer` | P0 |
| 600 模块端解析 | `Protocol_Package_Save_Result` | `BatteryModuleFrameDataParserService`、实时表 mapper | P0 |
| 电池组计算 | `protocol_package.c` 聚合逻辑 | `BatteryModuleGroupCalculationService` | P0 |
| 当前状态寄存器 | `Battery_State_Register` | `BatteryModuleGroupRealtime`、Modbus read mapping | P0 |
| 通信/模块故障状态 | `alarm.c`、`alarm.h`、8D 故障位 | `battery_device_state`、通信告警适配 | P0 |
| 600 显式控制 | `server.c`、`protocol_package.c`、`rs485.c` | `BatteryCollectorCommandService`、命令队列 | P1 |
| 告警阈值和过滤 | `alarm.c`、`alarm.h` | `BatteryModuleAlarmAdaptService`、`AlarmContextProcessor` | P1 |
| SOC/SOH/容量 | `soc.c`、`capacity.c` | 轮询外后处理、预测缓存、统计服务 | P1 |
| JSON/TCP 切源 | M460 网络端语义 | `BatteryModuleRealtimeAdapterService`、`DataReportJob` | P1 |
| 上行 Modbus RTU | `modbus.c` | `ModbusRtuServer`、读写映射服务 | P1 |

## 3. 十次短迭代路线

## 4. 全局禁止事项

1. 不恢复 980 PC/网络端协议为运行链路。
2. 不把 87/8D payload 直接塞进标准实时模型。
3. 不在没有 600 或状态来源时伪造电池组运行状态。
4. 不把 SOC/SOH/容量算法写进轮询线程。
5. 不提交 `03code/energy/sql/rysqlite3.db` 运行态数据。
6. 不维护 `03code/energy/src/main/resources/dist`。
7. 不回退已有用户或其他任务产生的脏改。

## 5. 每轮执行模板

每轮保持短迭代：

1. 需求 agent：从本计划挑选一个小任务，确认边界和验收命令。
2. 开发 agent：只修改该任务所属文件，避免跨模块扩散。
3. 测试 agent：补或执行最小测试集合。
4. 审查提交 agent：检查 diff、脏工作区边界和提交范围。
5. 主线程：只 stage 本轮文件，提交一个小 commit。

每轮提交前至少执行：

```bash
git status --short
git diff --check
```
