# M460 未整合能力全局盘点

日期：2026-06-18

本文用于全局核对 M460 已具备但 `energy` 尚未完整整合的能力。结论以当前代码、`M460协议功能对照表.md`、`M460字段来源矩阵.md`、`M460_87告警规则表.md`、`SH_Modbus寄存器映射草案.md` 和 `M460_followup_plan_20260616.md` 为准。

状态说明：

- `implemented`：已有明确代码落点，主链路基本闭合。
- `partial`：已有模型、命令或适配入口，但调度、状态、结果、外部输出或现场联调未闭合。
- `planned`：已进入后续计划任务。
- `deferred`：需要后处理、历史状态、业务确认或现场联调后再做。
- `excluded`：M460 板级/中间协议能力，当前不作为 `energy` 默认整合范围。

## 1. 总体结论

M460 核心采集能力已经部分整合到 `energy`：600 节 `01/81` 轮询、单体/组实时表、组计算、快照新鲜度、部分 600 控制命令、部分 Modbus 读取和告警适配都有落点。

仍未完整整合的主要不是“能否拼命令”，而是以下闭环：

1. 外部读取统一口径：JSON/TCP、页面、统计、screen、Modbus 告警/参数寄存器仍未全部切到标准实时快照和标准告警模型。
2. 测试计划闭环：`OptBatteryController` 的 `dev_battery_opt` 计划配置、到点触发、立即执行、停止、互斥、结果落库还没有统一接入 M460/600 独立采集命令体系。
3. 测试流程闭环：内阻测试、连接条电阻测试已有命令基础，但地址推进、周期读取、超时恢复、统计刷新和外部可观测状态仍不完整。
4. 告警能力闭环：M460 87/8D 中可由实时数据生成的告警需要继续落到标准告警模型；过滤、屏蔽、解除、无来源告警排除需要单独任务。
5. 长周期算法：SOC/SOH/容量/核容/备电等 M460 由周期任务和持久状态维护，`energy` 不能在采集线程临时硬算，需要轮询外后处理服务。
6. 板级硬件与网络管理：蜂鸣器、LED、LCD、继电器、ADC/DAC、RTC、SD、OTA、IP/MAC/云端参数等默认不整合，除非有明确业务和硬件承接。

## 3. 需要优先补的任务

优先级按“功能主线”和“外部可见风险”排序：

1. `TASK-BAT-FUNC-SNAPSHOT-001` / `TASK-BAT-FUNC-FRESHNESS-001` / `TASK-BAT-FUNC-MODBUS-CACHE-001`：先稳定高频读取快照和新鲜度。
2. `TASK-BAT-FUNC-JSONTCP-FIELDS-001`：逐项盘点 JSON/TCP 输出字段，确定来源和不支持项。
3. `TASK-BAT-FUNC-OPT-PLAN-001`：把 `OptBatteryController` 测试计划接到独立采集命令体系，补到点调度或 dispatcher。
4. `TASK-BAT-FUNC-CONNECT-RESISTANCE-001`：闭合连接条测试的地址推进、`11/91` 周期读取、计算和结果落库。
5. `TASK-BAT-FUNC-INTERNAL-RESISTANCE-001`：闭合内阻测试的触发、运行态、响应、统计和外部状态。
6. `TASK-BAT-FUNC-MODBUS-READ-ALARM-001` / `TASK-BAT-FUNC-MODBUS-READ-PARAM-001`：补 Modbus 告警/参数读取。
7. `TASK-BAT-FUNC-MODBUS-WRITE-001`：在命令闭环稳定后扩展写寄存器白名单。
8. `TASK-BAT-FUNC-ALARM-COVERAGE-001` / `TASK-BAT-FUNC-ALARM-FILTER-001` / `TASK-BAT-FUNC-ALARM-SHIELD-001`：补标准告警覆盖、过滤和屏蔽/解除。
9. `TASK-BAT-FUNC-SOC-STATE-001` / `TASK-BAT-FUNC-CAPACITY-STATE-001`：后处理长期状态设计完成后再迁移 SOC/SOH/容量。

## 4. 明确不应默认整合的能力

以下能力虽然 M460 有源码或协议语义，但当前不应作为 `energy` 默认整合任务：

- 980 PC/网络端作为运行中间协议。
- M460 网络 IP、MAC、云服务器、server/client mode 管理。
- 蜂鸣器、LED、LCD/TFT、按键、红外、继电器、ADC/DAC、GPIO、WDT、RTC、SD、Flash、FRAM/EEPROM 等板级硬件抽象。
- OTA、恢复出厂、清主机数据等高风险维护能力。
- Modbus TCP，除非部署明确要求。
- 热失控、氢气、网络、传感器等无明确 energy 数据源的告警。
- 从单轮采集数据临时合成 SOC/SOH/容量。

## 5. 后续核验方法

执行任意 M460 能力补齐任务前，先按以下顺序核验：

1. 用 `.codegraph` 查询涉及的 controller/service/mapper/consumer 和调用影响面。
2. 用 `rg` 对照 M460 源码、协议文档和当前 Java 入口，确认是否已有局部实现。
3. 先确认能力归属：采集主链路、命令控制、测试计划、告警、后处理、外部读取、Modbus、硬件排除。
4. 对 `partial` 项优先补闭环，不重复造第二套模型。
5. 对 `deferred/excluded` 项先写清原因，不为了“对齐 M460”恢复旧 980 runtime 或板级固件能力。
