# M460 87/8D 告警规则表

> 更新时间：2026-08-05
> 对照源码：`02sourceCode/M460_Series_BSP_CMSIS_V3.00.002/SampleCode/NuMaker_M467HJ/LwIP_TCP_EchoClient/MyFiles/alarm.c` + `alarm.h`

## 概述

M460 固件在 `alarm.c` 中实现告警阈值比较和位设置，通过 87（告警）和 8D（故障）命令上报给 energy。energy `BatteryAlarmHandler` 解析 payload 中的位并调用 `IAlarmLogService.alarmBattery` 落库。

**数据格式：**
- 87 组级：3 组 × 2 字节（一般/异常/严重），每组 status1 低 6 位 + status2 全 8 位 = 14 有效位
- 87 单体：每单体 3 组 × 2 字节 + 编号 = 7 字节
- 8D 组级：1 字节 8 位
- 8D 单体：每单体 2 字节（编号 + 1 字节故障位）

**告警值编码：** `"0"` = 正常，非 `"0"` = 告警（值为 `AlarmLevelEnum` 的 dictValue）

---

## ⚠️ 关键问题：M460 物理 bit 与 energy 字符串下标需换算复核

经固件源码分析确认：M460 固件对 87 payload **未做 bit 重排**。`alarm.c` 中 `Battery_Warning_OutPut_Result` 将告警位写入 `Array_Alarm_Real_Result` 结构体，`Server_Get_Battery_Array_Warning_State_Function` 通过 `memcpy` 直接复制到 87 payload。因此 `alarm.h` 的 bit 定义就是 87 payload 的实际 bit 布局。

M460 `alarm.h` 定义的 `ARRAY_BYTE1` bit 位：

| M460 bit | M460 常量 | M460 含义 |
|----------|-----------|-----------|
| 0 | `BATTERY_ARRAY_WARNING_VOLTAGE_HIGH` | 组压高 |
| 1 | `BATTERY_ARRAY_WARNING_VOLTAGE_LOW` | 组压低 |
| 2 | `BATTERY_ARRAY_WARNING_CHARGE_CURRENT_BIG` | 充电电流大 |
| 3 | `BATTERY_ARRAY_WARNING_DISCHARGE_CURRENT_BIG` | 放电电流大 |
| 4 | `BATTERY_ARRAY_WARNING_TEMPERATURE_HIGH` | 环境温度高 |
| 5 | `BATTERY_ARRAY_WARNING_TEMPERATURE_LOW` | 环境温度低 |

energy `dealPackWarnParam` 的 `setLevel` 调用：

| energy bit | energy itemCode | energy 含义 |
|------------|-----------------|-------------|
| 0 | ZWDD | 环境温度低 |
| 1 | ZWDG | 环境温度高 |
| 3 | ZCGDLGJ | 充/放电电流大 |
| 4 | ZDYGF | 组压低 |
| 5 | ZDYGC | 组压高 |

**复核结论：** 不能直接把 energy `setLevel(status, 0..13, ...)` 的数字等同于 M460 C 源码里的 `1 << bit` 物理 bit。energy 先调用 `CodingUtil.hexString2binaryString` 得到类似 `00000001` 的字符串，再用 `status.charAt(index)` 取位；因此：

| energy 字符串下标 | 对应物理 bit |
|---|---|
| 0 | bit7 |
| 1 | bit6 |
| 2 | bit5 |
| 3 | bit4 |
| 4 | bit3 |
| 5 | bit2 |
| 6 | bit1 |
| 7 | bit0 |

组级 87 还存在 `status1.substring(2) + status2` 处理，`status1` 前 2 位作为等级位剔除后，后 6 位再与 `status2` 拼接。因此对照关系必须按“payload 物理 bit -> binaryString 字符串下标 -> substring 后下标 -> itemCode”逐项换算。

**当前处理原则：** 物理 bit 与字符串下标口径需换算复核。经 2026-06-12 详细测试复核，原有 `BatteryAlarmHandler` 中 M460 物理 payload 各个告警/故障位到 ItemCode 的映射完全匹配无误。已在 `BatteryAlarmHandlerTest` 中对 87 组级告警、87 单体告警、8D 组级故障、8D 单体故障的物理 bit 边界进行了详尽单测验证，复核无误，已固化单测守护，确保解析安全等价性。

**代码固化：** `BatteryAlarmBitMapping` 已提供字符串下标与物理 bit 的双向换算，以及组级 87 有效 14 位的来源字节/物理 bit 换算；`BatteryAlarmBitMappingTest` 已覆盖 `01 -> 00000001`、普通 bit 映射和组级 87 边界映射。同时已在 `BatteryAlarmHandlerTest` 中补齐了针对 M460 87/8D 告警与设备故障映射的边界单测。后续复核 itemCode 时应优先使用该口径，避免直接把 `setLevel(status, index, ...)` 的 `index` 当作 M460 物理 bit。

## M460 告警处理流程

```
alarm.c:
  Battery_Alarm_Set_Bit_Value(Array, Monomer, Type, Bit, ON/OFF)
    ↓
  Battery_Warning_OutPut_Result()
    ↓ 遍历 4 个通道
    ↓ ALARM_FILTERING: 连续 N 次超限才确认
    ↓ 合成 Array_Commonly/Abnormal/Critical_Byte1/Byte2
    ↓
  Battery_Get_Result(Array, Monomer, Warning_Type, Point)
    ↓ 组装 Battery_Alarm_Result
    ↓ Array_Warning_Byte1 = Commonly_Byte1 | (type << 6)
    ↓
  打包为 87 payload → 发送给 energy
```

```
energy BatteryAlarmHandler:
  toWarnDecoder(info)
    ↓ 解析 packNum, alarmBatterySum, packStatus, packBatteryStatus
    ↓
  dealPackWarnParam(status, level, warnParam)
    ↓ 转 binaryString 并按字符串下标映射 itemCode（需按物理 bit 换算复核）
    ↓
  alarmLogService.alarmBattery(config, packNum, modelNum, warnParam, batteryReportLog)
    ↓ 阈值比较、告警落库、恢复处理
```

## energy 当前告警流程与 M460 差异

### 1. 标准 600 实时告警主流程

600 节采集模块完成一轮组数据和单体数据后，依次经过：BatteryModuleAlarmAdaptService 构建告警候选；AlarmContextProcessor 合并实时阈值和 battery_device_state 状态上下文并判断批次新鲜度；BatteryAlarmEvaluationService 统一提交告警并按本轮单体集合处理恢复；AlarmLogServiceImpl.alarmValid 匹配 ConfigAttribute、写入 dev_alarm_log 并维护告警缓存。

通信、在线、模块超时和组 246 新鲜度告警由 BatteryAlarmStateContextService 从 battery_device_state 构建，不再依赖查询时临时合成 AlarmLog。DataReportJob 从告警缓存上报第三方平台，页面和当前态查询也主要从该缓存读取。

### 2. M460 recValue 恢复值

AlarmItemLevelVo 已有 recFlag 和 recValue 字段，旧 BatteryParamsHandler 会把恢复值写入 ConfigAttribute.listLevel。当前 AlarmLogServiceImpl.getLevel 已按历史告警缓存消费这两个字段；alarmValid 发现最新值达到恢复条件时才把缓存告警置为已处理。

结论：当前实现不是“离开告警区间即恢复”，而是仅在存在同等级历史告警且配置了恢复值时，按恢复值和短时过滤处理；无缓存、历史等级无法匹配或恢复参数缺失时仍按当前最高命中等级处理。状态语义如下：

| 当前历史状态 | 最新值 | 预期动作 |
|---|---|---|
| 无未恢复告警 | 落入告警区间 | 创建告警 |
| 有未恢复告警 | 仍超限或未达到恢复区间 | 保持告警，必要时更新等级/当前值 |
| 有未恢复告警 | 达到 recFlag/recValue 恢复条件 | 关闭告警 |
| 有未恢复告警 | 离开告警区间但未达到恢复条件 | 按现场 M460 逻辑确认，不能直接关闭 |

多等级恢复值归属、模拟量高/低方向、边界是否包含、恢复值为空时的退化规则，以及等级切换是否重置恢复状态，已按本节和 2.3 的最小改造口径处理；仍需通过现场规则矩阵和测试继续验证。

### 2.1 M460 源码确认结论

源码依据：

- 02sourceCode/M460_Series_BSP_CMSIS_V3.00.002/SampleCode/NuMaker_M467HJ/LwIP_TCP_EchoClient/MyFiles/alarm.h
- 02sourceCode/M460_Series_BSP_CMSIS_V3.00.002/SampleCode/NuMaker_M467HJ/LwIP_TCP_EchoClient/MyFiles/alarm.c

M460 的告警值和恢复值不是通过单个参数加回差计算，而是每个告警项直接配置一对参数：

| 告警项参数 | 恢复项参数 | 说明 |
|---|---|---|
| 0x01 | 0x02 | 单体电压过高告警/恢复 |
| 0x03 | 0x04 | 单体电压过低告警/恢复 |
| 0x05 | 0x06 | 单体浮充电压过高告警/恢复 |
| 0x07 | 0x08 | 单体浮充电压过低告警/恢复 |
| 0x09 | 0x10 | 单体电压不均告警/恢复 |
| 0x13 | 0x14 | 组电压过高告警/恢复 |
| 0x15 | 0x16 | 组电压过低告警/恢复 |
| 0x17 | 0x18 | 组浮充电压过高告警/恢复 |
| 0x19 | 0x20 | 组浮充电压过低告警/恢复 |
| 0x21 | 0x22 | 充电过流告警/恢复 |
| 0x23 | 0x24 | 放电过流告警/恢复 |
| 0x25 | 0x26 | 环境高温告警/恢复 |
| 0x27 | 0x28 | 环境低温告警/恢复 |
| 0x31 | 0x32 | 单体高温告警/恢复 |
| 0x33 | 0x34 | 单体低温告警/恢复 |
| 0x35 | 0x36 | 单体温度不均告警/恢复 |
| 0x37 | 0x38 | 内阻过大告警/恢复 |
| 0x39 | 0x40 | 内阻不均告警/恢复 |
| 0x41 | 0x42 | 内阻过小告警/恢复 |
| 0x45 | 0x46 | 氢气浓度告警/恢复 |
| 0x49 | 0x50 | SOC 低告警/恢复 |
| 0x51 | 0x52 | SOH 低告警/恢复 |

这里的“间隔 1”是参数号编码关系，不代表 energy 的 paramsNumber 可以作为唯一告警项标识。
M460 的 Battery_Alarm_Items_Address 会重新排列这些参数项的处理顺序，不能按参数号自然排序推导
87/8D 物理位。

M460 每轮处理逻辑为：

1. Battery_Alarm_Warning_Item_Parameter 分别读取 Warning_Item 和 Reset_Item。
2. Battery_Alarm_Warning_Item_Count_Status 将当前采样值与两条边界比较。
3. Battery_Warning_Item_Test_Status 读取当前告警位，仅在目标状态与当前位状态不一致时置位或清位。
4. 结果经 ALARM_FILTERING 过滤后进入 87 告警状态输出。

逻辑方向已经由 alarm.c 的 Logical_State 明确：

| 逻辑方向 | 进入告警 | 恢复告警 |
|---|---|---|
| 正向告警 | 当前值 >= Warning_Item | 当前值 <= Reset_Item |
| 负向告警 | 当前值 <= Warning_Item | 当前值 >= Reset_Item |

因此恢复值的真实语义是独立的恢复边界，不是“最新值不再满足告警阈值就立即恢复”。例如高温告警阈值为
Warning_Item，恢复必须继续降到 Reset_Item；低温告警阈值为 Warning_Item，恢复必须升到 Reset_Item。

M460 还定义 ALARM_FILTERING_NUMBER=2。过滤器对告警字节和单体告警字节分别累计连续命中次数，
非命中会清零，达到过滤次数后才形成稳定告警状态。energy 后续如需复刻 M460 行为，必须分别确认：
采集周期、连续次数、恢复侧是否同样过滤，以及组级和单体级是否共用计数器。

当前可确定的实现差异：

- M460 在设备侧直接比较 Warning_Item/Reset_Item 并维护告警位。
- energy 新链路按 ConfigAttribute.listLevel 的告警区间判断；存在同等级历史缓存时额外消费 recFlag/recValue。
- energy 的 recFlag/recValue 已作为兼容承载字段接入恢复判断；参数号矩阵和现场方向仍需继续核对，不能据此补造未映射的告警项。
- 后续应先建立“ItemCode、M460 告警参数号、M460 恢复参数号、逻辑方向、来源字段、87/8D 位”的完整矩阵。

### 2.2 energy 最小改造方案（待确认）

当前倾向于不新增复杂状态对象，直接扩展 AlarmLogServiceImpl.getLevel 的输入：

getLevel(configAttribute, value, cacheLog)

建议流程：

1. 先按当前采样值匹配当前告警等级。
2. 只有模拟量且存在未恢复历史告警时，才根据 cacheLog.alarmLevel 找到历史告警等级。
3. 历史等级存在 recFlag/recValue 且当前值未达到恢复值时，返回历史告警等级，阻止 alarmValid 提前关闭告警。
4. 当前值达到历史恢复值后，返回当前匹配结果；当前结果为空则关闭告警，当前结果仍为告警则更新当前告警。
5. 历史规则没有恢复值时，保持现有 energy 的区间恢复行为。

该方案利用现有 alarmValid 的返回值语义，不新增告警状态表，也不改变非模拟量告警流程。

#### 尚未确定的逻辑

以下问题在确认前不能进入代码实现：

| 问题 | 当前歧义 |
|---|---|
| 当前告警与历史告警“不一致”的定义 | 是当前结果为空才算不一致，还是当前等级变化也算不一致 |
| 历史告警仍未达到恢复值但当前值进入另一告警等级 | 应保持历史等级，还是允许升级/降级后使用新等级规则 |
| 当前值处于告警区间外但未达到恢复值 | 应保持告警，还是 M460 只维护告警位而不维护 energy 的历史等级 |
| 恢复值边界 | M460 使用小于等于/大于等于，energy 是否完全保持相同边界 |
| 基准值换算 | recValue 是否与 hightValue/lowValue 一样参与 standValue 换算 |
| 找不到历史 alarmLevel 对应规则 | 应退化到当前匹配结果，还是保持历史告警避免误恢复 |
| 多等级配置 | 一个 ItemCode 多个等级时，恢复值属于历史等级还是整个 ItemCode |
| 屏蔽告警 | 屏蔽期内是否完全跳过恢复值判断，屏蔽到期后的第一次采集如何处理 |

目前文档结论确认采用 `getLevel(configAttribute, value, cacheLog)` 的最小改造方向；多等级、屏蔽生命周期和 M460 连续过滤仍需专项测试与现场核对。
恢复值状态机已落地，后续补充 M460 参数矩阵、energy 多等级和屏蔽生命周期测试；M460 的 ALARM_FILTERING 连续过滤继续作为独立任务处理。

### 3. ItemCode 与 M460 规则对应结论

ItemCode 不是 M460 87/8D 告警项的一一镜像，而是 energy 业务字典和历史兼容编码：

| 类型 | 当前情况 | 结论 |
|---|---|---|
| 一项多语义 | ZCGDLGJ 同时承接充电过流和放电过流 | 无法仅凭 itemCode 区分两个 M460 物理 bit |
| M460 有、energy 无直接来源 | 热失控、氢气、脱离母线、网络和多个传感器故障 | 保持 unsupported，不凭旧位图补告警 |
| energy 有、600 当前无生产方 | DTDYBJ、DTDCWDBJ、DTNZBJ、DTFCDYG/D、DTLJTGJ 等 | 需实时统计、测试流程或现场协议提供来源 |
| 历史语义遗留 | DTGB 旧参数曾复用 SOH 参数，当前读取 swollenVoltage | 鼓包基准和字段来源需现场确认 |
| 参数编号重复 | ZSOHDGJ 与 DTGB 的 paramsNumber 都为 51 | 必须使用 itemCode，不得使用 paramsNumber 唯一识别 |
| 组压来源差异 | 新 600 告警使用 externalVoltage，缺失时退化 packVoltage | 不按旧 M460 口径无条件替换字段 |

因此“能否生成”必须同时标记协议位映射和当前 600 数据面生产方，不能仅根据枚举存在判断功能已实现。

### 2.3 已确认的 energy 恢复业务语义

以高温告警为例：

- 告警阈值：当前值大于 45；
- 恢复值：当前值小于 43；
- 当前值 50：命中告警等级，保持告警并清零恢复次数；
- 当前值 44：未命中告警，也未命中恢复值，累计恢复候选次数，连续达到 3 次后按当前等级结果处理；
- 当前值 42：命中恢复值，立即按不告警处理，不等待 3 次。

因此恢复值和连续次数承担不同职责：

| 当前值状态 | 处理 |
|---|---|
| 命中当前或更高告警等级 | 按告警处理，恢复次数清零 |
| 未命中告警且未命中恢复值 | 累计恢复候选次数，未满 3 次保持历史告警 |
| 命中恢复值 | 立即恢复，恢复次数清零 |
| 恢复候选次数达到 3 次 | 按当前最高命中等级处理；无命中则恢复 |

低限告警反向适用：低于告警阈值进入告警，高于恢复值立即恢复，处于两者之间累计恢复候选次数。
该语义是 energy 当前业务确认口径，后续实现和测试以此为准；它不是简单的“恢复值连续命中 3 次”。

## 除阈值/状态评估之外的告警维护入口

### 1. 前端告警屏蔽

页面经 AlarmLogController 调用 shiedAlarmLog：当前记录写为已处理，保存 shiedTime 和备注；屏蔽期内记录保留在缓存，alarmValid 直接返回；屏蔽到期后下一次评估才允许重新创建。这是“当前告警处置 + 一段时间抑制”，不是永久关闭告警配置。alarmFix 对屏蔽中的记录也会跳过关闭，后续应统一屏蔽、恢复和人工处置的状态语义。

### 2. 告警配置关闭/修改

ConfigAttribute.status、alarmConfig 或等级列表关闭时，alarmValid 会关闭当前调用 key 的告警，属性更新流程也调用 closeAlarmLog。但 closeAlarmLog 使用 modelNum=null 的组级 key，存在单体告警不被覆盖的风险。关闭配置时应明确是关闭组级、全部单体，还是只禁止后续产生。

### 3. 删除电池组

删除电池组时调用 alarmFix(packNum, false, null, null)，只把当前未恢复告警置为已处理；deleteBatteryAlarmLogByPackNum 不是删除电池组的统一动作。因此删除后重建相同 packNum 可能看到旧历史告警，且新旧设备身份没有区分。后续应明确“保留历史并隔离设备生命周期”或“删除历史并同步清理告警缓存、实时快照、设备状态和统计”，不能只关闭当前告警后假设历史已清理。

### 4. 单体未采集

新链路对本轮实际出现的单体调用 alarmFix(..., true, currentBatchCellNums, ALL_CELL_ALARM_CODES)，将未提交的单体告警关闭。这会避免上一轮告警残留，但单体短时丢帧也会被立即视为恢复，造成告警记录切断。后续应区分完整批次确认缺失和单体暂时超时/部分响应，引入连续多轮确认或新鲜度宽限窗口；空单体批次不能触发全量恢复。
