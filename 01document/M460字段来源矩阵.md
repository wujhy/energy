### 3.2 ⚠️ 组级 bit 位口径复核

经固件源码分析确认：M460 固件对 87 payload **未做 bit 重排**。`alarm.c` 中 `Battery_Warning_OutPut_Result` 将告警位写入 `Array_Alarm_Real_Result` 结构体，`Server_Get_Battery_Array_Warning_State_Function` 通过 `memcpy` 直接复制到 87 payload。因此 `alarm.h` 的 bit 定义就是 87 payload 的实际 bit 布局。

```
M460 ARRAY_BYTE1 (alarm.h):  bit0=VOLTAGE_HIGH  bit1=VOLTAGE_LOW  bit2=CHARGE_CURRENT
                              bit3=DISCHARGE_CURRENT  bit4=TEMP_HIGH  bit5=TEMP_LOW

energy setLevel 调用下标:     index0=ZWDD(温度低)  index1=ZWDG(温度高)  index3=ZCGDLGJ(电流)
                              bit4=ZDYGF(组压低)  bit5=ZDYGC(组压高)
```

**复核结论：** 上表不能直接判定错位，因为 energy 的 `setLevel(status, num, ...)` 中 `num` 是 `binaryString` 字符串下标，不是 M460 C 源码 `1 << bit` 的物理 bit 编号。`hexString2binaryString("01")` 形如 `00000001` 时，字符串下标 0 对应物理 bit7，下标 7 对应物理 bit0。

组级 87 还会执行 `status1.substring(2) + status2`，即 status1 前两位等级位被剔除后再拼接 status2。因此必须按以下链路复核：

```text
M460 物理 bit -> 87 payload 字节 -> binaryString 字符串下标 -> substring 后下标 -> energy itemCode
```

**当前处理原则：** energy 旧告警解析已有现场验证，先视为正确。本文档只记录需要复核的换算关系，不直接要求修改 `BatteryAlarmHandler`。

### 3.3 M460 告警处理流程

```
M460 alarm.c:
1. Battery_Alarm_Set_Bit_Value(Array, Monomer, Type, Bit, ON/OFF)
   → 设置/清除指定字节的指定位
2. Battery_Warning_OutPut_Result()
   → 遍历 4 个通道，按 alarm grade 处理
   → 过滤（ALARM_FILTERING）：连续 N 次超限才确认
   → 合成 Array_Alarm_Real_Result（Commonly/Abnormal/Critical）
3. Battery_Get_Result(Array, Monomer, Warning_Type, Point)
   → 组装 Battery_Alarm_Result（含 type 标记）
   → Array_Warning_Byte1 = Commonly_Byte1 | (type << 6)
   → Array_Warning_Byte2 = Commonly_Byte2
4. 打包为 87 payload → 发送给 energy

energy BatteryAlarmHandler:
1. toWarnDecoder(info) → 解析 packNum、alarmBatterySum、packStatus、packBatteryStatus
2. dealPackWarnParam(status, level, warnParam) → 按 bit 位映射 itemCode
3. dealSingleWarnParam(status, level, warnParam) → 按 bit 位映射 itemCode
4. alarmLogService.alarmBattery(config, packNum, modelNum, warnParam, batteryReportLog)
   → 阈值比较、告警落库、恢复处理
```
