   - 补偿判定：综合 `optLogService.selectRunningList(packNum)`、`BatteryModeStatusService.get(packNum)`、采集通道 `pendingCommand`、`queuedModuleCommands`、最后发送/响应/超时时间和任务类型判断，不能只看单一状态。
   - 保守规则：如果 running optLog 存在但 mode 已 idle，且采集侧无相关 pending/queued，超过阈值后标记为超时/异常结束；如果 mode running 但无相关 pending/queued，且最后状态更新时间超过阈值，执行 `markStopped(..., false)` 并关闭业务日志。
   - 复杂场景：`BatteryModeStatusService` 为 running 且队列有 pending/queued 时，仍可能不是当前测试的有效推进，例如队列里是其他类型命令、只剩轮询/维护命令、pending 已超出响应阈值但未被 timeout service 收口、或崩溃恢复后队列状态丢失但 mode/optLog 仍残留。补偿服务必须按 packNum、mode、业务日志ID/命令日志ID、协议类型和更新时间关联判断，避免被“有队列”这个表象误导。
   - 阈值策略：不同测试类型使用不同超时窗口；`_1/_2` 整组测试允许长耗时但必须观察是否有持续推进，`_6` 单命令可用较短窗口；未确认现场耗时前只做保守超时，不做激进清理。
   - 已完成第一阶段：新增 `BatteryOptRuntimeRecoveryService`。系统重启后视为所有运行中任务已停止，`CacheInit` 启动后会全量关闭 running `dev_opt_log`，并按 `_1/_2/_6` 对应模式执行 `markStopped(..., false)`；`BatteryOptScheduleJob` 每轮计划执行前按 packNum 调用保守补偿，只在 running 日志超过阈值且 `BatteryModeStatusService` 已非同组 running 时关闭残留日志，避免运行期误停真实测试。
   - 暂不激进清理：`BatteryModeStatusService` 仍为 running、且队列可能有 pending/queued 的场景，本阶段不直接 markStopped；后续需要补齐采集通道队列快照/最后推进时间/业务日志ID关联后再处理，避免误停真实测试。
4. `TASK-M460-LOG-FUNC-001`：区分业务测试日志和模块命令明细日志。
   - 背景：测试计划和用户可感知的业务 `optLog` 必须保留；`_99` 模块命令明细主要用于排障，若所有成功命令都落库会放大 SQLite/数据库存储压力。
   - 当前结论：`optLogId` 表示单条模块命令明细日志，`businessOptLogId` 表示一次业务测试整体日志；`_1` 整组内阻必须保留 `_1` 业务日志，单节 `02/82` 明细继续按 `_99` 表示。
   - 后续策略：增加配置开关或落库策略，默认保留业务日志；模块命令明细可选择“仅失败/超时/拒绝落库”“调试开关打开才全量落库”或“成功明细只保留内存/短期清理”。
   - 验收边界：关闭非必要明细日志后，计划调度、页面状态、停止命令、异常补偿仍以业务日志和 `BatteryModeStatusService` 为准，不依赖 `_99` 成功明细存在。
   - 已完成第一阶段：新增 `moduleCommandSuccessLogEnabled` 配置，默认从源头不创建 `_99` 模块命令明细日志，避免 pending 插入后再删除带来的数据库写入压力。`_1` 业务日志、`_2/_6` 业务类型日志不受该开关影响，计划调度和异常补偿继续以业务日志与 `BatteryModeStatusService` 为准；需要排查单条模块命令过程时可打开该配置保留全量 `_99` 明细。
